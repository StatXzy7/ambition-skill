# Ambition：把提示词往高、深、广改写

- 模式库：`references/patterns.md`（菜单、通用骨架、各条模式、反模式、变更记录）
- 使用者语境：`references/contexts.md`（工作类型、验证分级、已登记的验证器与原始材料路径、对外口径）。这是一份模板，由使用者按自己的项目填写；没填的部分就当它不存在，不要猜。

## 为什么需要这个技能

人给模型下的任务通常问得太少：写成名词（"做一份 PPT"），只给消化过的摘要，让模型自己评价自己。这个技能从三个方向把任务往上拉：

- 高度：追问目标背后的目标；
- 深度：用原始材料和专家真正用的工具，目标定得激进；
- 广度：借用长期在解决同一个问题的其他领域的方法。

拉高的同时有一条硬约束。模型被逼紧时，最省事的"达成"方式是悄悄改尺子：放宽阈值、换计时口径、只挑有利的样本。所以激进目标出现的地方，同一个提示词里必须有冻结的验证器和写明的禁止项。另一条原则是做事激进、对外说话保守：给合作方看的材料里，激进只体现在"要对方做什么决定"上，引用的数字一律用同口径、带限定的版本。

## 按参数选模式

看用户传进来的参数的开头：

- `list`（可带关键词）→ 列菜单，见下文"list"
- `add …` → 往库里加模式，见下文"add"
- `note <ID> …` → 记录实战效果，见下文"note"
- 其他内容 → 把它当作原始提示词，走"改写流程"
- 没有参数 → 用对话里用户最近描述的任务；如果也没有，就请用户贴出原始提示词

## 改写流程

1. **读任务。** 判断类型，以及任务的大小。类型有五种：工程实现或优化（包括对齐参考实现的移植与重写）、研究与选题、对外沟通（PPT、会议、合作方）、分析与决策、其他。

2. **诊断。** 对照下面四个问题，找出最弱的一两处，不需要每一处都改：
   - 高度：写的是名词或动作，还是一个结果？目标背后的目标是什么？做完之后还要开会讨论的话，就再往上提一层。
   - 深度：给模型的是原始材料还是摘要？有没有点名专家会用的工具？目标是不是定得保守了？
   - 验证：除了模型自己，还有什么能证明结果是对的？这个验证器冻结了吗？口径上有没有能钻的空子？
   - 广度：有没有别的领域长期在解决同一个问题（同一个动词）？

3. **取材。** 在当前工作目录里快速找能填进提示词的真东西：验证脚本、冻结的基线、原始数据、之前的报告、问答准备、对外口径的限定条件。先看 `references/contexts.md` 里登记过的路径。这一步花几分钟就够，不要做成一次调研。路径和数字都从源文件里读，并注明出处，不要从记忆里抄，因为它们会过期。找不到的就写成占位符，不要编。
   - 如果任务要改某个代码仓库，先看它的当前状态：在哪个分支、有没有未提交的改动、有没有别的会话正在里面编译或编辑。然后在提示词里写清三件事：在哪个分支做、哪些改动不许动、工作区被占用时停下来找用户。用户经常同时开几个会话，执行者如果不知道这些，第一步就可能覆盖掉别人的工作。
   - 如果已有的做法或材料里已经回答过这个问题，改写的方向应该是"在已有结论上往前推"，而不是"再做一遍"。例如已经有同主题的调研，就先证伪它，再只补查过期或没核实的部分。

4. **选 2–4 个模式。** 不要全用。全部叠上去，提示词会变得又长又散，真正关键的那条要求反而被淹没。按诊断出来的短板来选，常见起点如下：
   - 工程任务：H2、D2、V1、D4
   - 选题与调研：S1、H5、D6、R4
   - 对外沟通：R1、H3、P1、V3
   - 分析与决策：H1、D4、D5、V2

5. **写改写后的提示词。**
   - 写成一个可以直接复制的代码块，使用用户的语言。
   - 从 patterns.md 的"通用骨架"里挑这个任务用得上的槽位，用不上的删掉。
   - 激进目标只用于内部工作，而且同一个提示词里必须同时有冻结项和禁止项。对外材料里的数字一律同口径、带限定。
   - 不写角色扮演（"你是 XX 专家"）。直接写出专家会用的工具和方法，并要求模型真的去用。
   - 不编造。不确定的事实写成 `{需要你填：…}`，例如合作方是谁、关心什么，或者别人做到过什么、作为参照。不要猜。
   - 规模要和任务匹配。小任务是指几分钟到一小时能做完、只动一两个文件的任务，例如改名、修一个已定位的 bug、改一段文字。这类任务只用一个模式（通常是 V1，或者一条"改动前后行为不变"的检查），改写后的提示词控制在 15 行以内，不派子 agent，也不跑循环。验证写一句话说清"比什么、怎么比"就够了，不要展开成一套测试方案。把"改个变量名"写成登月计划，只会浪费用户的时间。
   - 大任务可以写长，但长度要花在项目特有的事实和防作弊条款上，不要花在通用的套话上。

6. **按这个结构输出：**

   **诊断**：两三句话，说明原提示词最缺什么。

   **用到的模式**：每个一行，格式是"`ID 名字`：为什么用它"。

   **改写后的提示词**：一个代码块。

   **需要你定的**：最多三项，只列只有用户能决定的事，例如目标数字、谁拍板、成功标准。

   **下一步**：问用户要不要直接按改写后的提示词执行。如果是长任务，顺带建议执行方式：在当前会话里做、派子 agent 并行，或者跑无人值守循环。

7. **执行与回收。**
   - 用户说执行，就把改写后的提示词当作任务，在当前会话里完成。
   - 做完后问一句哪个模式起了作用；用户回答后，用 `note` 记进库里。
   - 如果取材时发现了 contexts.md 里没登记的验证器、项目或对外口径，结束时提议补登进去。

## list

1. 把 patterns.md 里的菜单表原样输出。
2. 如果用户带了关键词（例如 `list 合作方`、`list 验证`），只列相关的条目。
3. 最后加一行用法提示：`/ambition <原始提示词>` 改写，`/ambition add …` 新增，`/ambition note <ID> …` 记录效果。

## add

用户给的可能是一句提示词、一段文章，或者一次好用的经历。

1. 按 patterns.md 里的"条目格式"提炼成一条模式。
2. 查重。和已有模式重叠过半的，合并进已有条目（补一个模板变体或一条实战记录），不要另开新条目。
3. 新 ID 取"维度字母 + 下一个序号"，已用过的 ID 不能复用。不确定属于哪个维度时，问用户。
4. 写入三处：菜单表加一行，正文加条目，文末变更记录加一行（日期、做了什么）。
5. 如果 contexts.md 的"手册副本"一节登记了一份副本（例如一份在线文档或本地笔记，供用户手写提示词时查看），把同样的改动同步过去。用户可能直接在副本里改过模板，所以动手之前先读一下这次要改的那一节。副本所在的工具不可用时，告诉用户需要手动同步。没有登记副本就跳过这一步。
6. 把改动展示给用户。

修改或废弃已有模式时，也按第 5 步同步副本。用户说在副本里改了某个模板时，读出改动，再同步回 patterns.md。

## note

1. 在对应条目的"实战记录"下面追加一行：`日期｜场景｜好/一般/差｜原因`。
2. 某个模式连续两次记为"差"时，提议修改或废弃它。废弃的条目移到文末的"已废弃"，ID 不复用。
