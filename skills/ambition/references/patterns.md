# 提示词模式库

主要来源：Felix Rieseberg，[How to be more ambitious: a tutorial for humans with models](https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/)；Matthew D. Schwartz，[Claude-shaped science](https://www.anthropic.com/research/claude-shaped-science)（Anthropic，2026-10-01）及其配套的 [BootLoops 协议](https://github.com/BootLoops-ai/skills)；以及作者在科学软件移植、性能优化和合作方沟通中的实践。模板是对这些想法的改写和补充，不是原文摘录。

如果你另外维护了一份给人看的副本（在线文档或本地笔记），在 `contexts.md` 的"手册副本"一节登记它。以本文件为准；新增或修改模式时同步过去，见 SKILL.md 的"add"一节。

用法：
- `/ambition list` 看菜单
- `/ambition <原始提示词>` 让 Claude 挑模式并改写
- `/ambition add …` 加新模式
- `/ambition note <ID> …` 记录某个模式的实战效果

维度字母：
- H 高度：目标背后的目标
- D 深度：专家的材料、工具和激进目标
- V 验证：外部评判
- R 广度：借别的领域
- P 合作方
- S 选题
- F 追问

## 通用骨架

改写时只保留这个任务用得上的槽位。

```
任务（用动词写）：在 {期限} 内，让 {谁} {做成/相信/决定 什么}。
目标：{激进指标}。这是能做到的；在拿出做不到的证据之前，不要降低目标。
参照：{一个真实做到过的类似例子}。
原始材料：{数据、代码、日志的路径}。不要用我写的摘要代替。
方法：先列出这个领域最强的人会用的工具和方法，再动手。
验证：{外部验证器、脚本或新数据}。验证器、阈值、计时脚本都冻结，不许修改。
禁止：{放宽阈值、换口径、挑样本、跳过失败的用例}。
完成的定义：{机器能检查的条件}。
做不到时交出：实测的瓶颈、离目标还差多少、要突破得换掉哪些假设。
```

## 条目格式

新增模式按这个格式写：

```
### <ID> <名字>
来源：<出处>｜加入：<日期>

用：<什么时候用>
别用：<什么时候别用>

    <模板，占位符写成 {…}>

常见失败：<模型或人最常见的走偏方式>

实战记录：
- 日期｜场景｜好/一般/差｜原因
```

## H 高度

### H1 目标背后的目标
来源：Felix，"altitude"一节｜加入：2026-10-19

用：任务写成了一个名词或一个动作（"做一份报告""修这个函数"），而它其实只是通往某个结果的一步。
别用：纯创作类任务，或者用户明确只要这一步的时候。

```
在动手之前，先回答：这件事做完之后，我希望接着发生什么？那件事背后又是什么目标？一直往上问，直到碰到一个可以检验的结果。
然后告诉我：按那个结果来衡量，我原来的任务是不是最好的一步？如果不是，更好的一步是什么？
如果做完以后还需要开会讨论，就再往上提一层，把会上要做的判断也一起做掉。
```

常见失败：一路往上问到"让公司赚钱"这种模型够不着的高度。停在模型手里有工具、能检验的那一层。

### H2 从修一个到保持一个性质
来源：Felix（"修一个崩溃"变成"保证应用不崩溃"）｜加入：2026-10-19

用：同一类问题反复出现，例如回归、精度漂移、性能回退、文档过期。
别用：一次性的问题。

```
不要只修 {这一个问题}。目标是让 {对象} 始终满足下面几条，并由你持续维护：
(a) {性质 1，例如：全量验收通过，用 {验收脚本}，阈值不改}；
(b) {性质 2，例如：性能相对冻结的基线不回退}；
(c) {性质 3，例如：每次提交都能对应到具体哪组参考输出}。
先列出：要独立维护这几条，你还缺什么权限、数据、环境（例如某组参考输出、Linux 机器、CI），我来补。
然后设计一个不需要我逐条派任务的循环：怎么触发、每轮检查什么、什么情况停下来叫我。
```

常见失败：循环建好了，却没有"什么时候叫人"的条件，结果要么一直空转，要么卡住了没人知道。

实战记录：

### H3 会议以决策收尾
来源：Felix，季度复盘第二步｜加入：2026-10-19

用：任何之后要开会、要汇报、要让别人拍板的产出。
别用：纯信息同步。

```
根据我们掌握的所有情况，这次 {会议/汇报} 最该推动的三个决策是什么？每个决策给出：
可选方案、对他们的利弊、对我们的利弊、我们希望对方选哪个、以及为什么这个选项对他们也是最优的。
如果某个决策对他们不利，直接说出来，并设计一个双方都能接受的版本。
```

常见失败：列出来的是"要讨论的话题"，而不是"要做的决定"。检查办法：每一项都要能用一个选项来回答。

实战记录：

### H4 换掉机制本身
来源：Felix，季度复盘第三步｜加入：2026-10-19

用：一项重复性的流程，例如周报、季度复盘、阶段汇报、人工验收。
别用：只做一次的事。

```
{这个流程} 存在的意义是：{它真正要达成的事，例如让合作方一直相信进展是真的、并能及时提出优先级}。
设计一个比现在的做法更好的机制（例如：对方能在自己机器上一键运行的验收包、自动生成的对照报告、数据一到就自动开跑的看板）。
用我们过去的记录（{日志或历史文件}）说明：这个机制本来能早多久暴露哪些问题。
然后给出它和现有方式并行运行 {一个月/一个季度} 的方案，以及到时候用什么指标判断要不要切换。
```

常见失败：设计得很漂亮，但没有用历史数据回测，无法证明它真的更好。

实战记录：

### H5 从极致成功倒推
来源：本库，由 Felix 的"更有野心"和"自我效能感"一节引申｜加入：2026-10-19

用：选题、立项，以及一个长期方向的开头。
别用：已经有明确交付物和期限的任务。

```
如果 {这个方向} 做到极致，{6 个月} 后我们发出去的是什么？具体到一个产出：一篇论文的标题和主图、一个榜单第一、一个被别人采用的开源工具，或者一个外部团队的正式采用。
从那里倒推：第 {N} 个月必须已经成立的是什么，第一周要做什么。
标出这条路上最可能先失败的一环，以及最便宜的办法：在第一周就测它。
```

常见失败：倒推出来的第一周仍然是"调研"。第一周应该至少有一个能跑的东西。

## D 深度

### D1 改深元提示词
来源：Felix 原文的元提示词（前四条）；第 5 条是本库补的｜加入：2026-10-19

用：拿不准怎么改的时候，先让模型自己改深。任何任务都能用。
别用：已经很清楚要什么、只差执行的时候。

```
我要的是这个任务更深的版本，不是更大的版本。改写之前先做五件事：
1. 这个领域顶尖的人在这里会做、而我没要求的事情；
2. 他们会从哪些最原始的材料入手，而不是用已经替我消化过的东西；
3. 他们会用的具体方法和工具，具体到库、求解器、数据库、统计模型的名字；
4. 除了你和我之外，什么能证明结果是对的；最好是你能自己运行、马上拿到反馈的东西；
5. 如果目标定得很激进，你最可能用什么方式"假装达成"，怎样提前堵住。
然后把我的提示词改写成准确要求这些的版本。

我的原始提示词：{…}
```

常见失败：改写变成了"范围更大"，而不是"更深"。第 1 句就是用来防这个的。

实战记录：

### D2 激进目标加冻结验证器
来源：Felix，"10 秒压到 0.2 秒"；一次独立审查的教训（报告里的"快 3.8 倍"，其实是 4 核对单线程、在不同的日子测的）｜加入：2026-10-19

用：有可量化的指标，并且有模型能自己跑的验证器和计时脚本。
别用：对外材料里的数字；还没有冻结验证器的时候（先用 V1 建一个）。

```
现状：{当前指标，写明口径：机器、线程数、对照对象}。
目标：同口径下 {激进指标，通常是现状的 10 倍以上}。参照：{一个真实做到过的类似例子}。先不要论证做不到。
冻结：{验收脚本、阈值、计时脚本、基线}，不许修改。每次改进都用同一个脚本复测，两边交替测。
禁止：放宽阈值、换计时口径（核数、日期、对照对象）、挑样本、跳过失败的用例。
先做 profile 和 roofline：每个热点离算法下限和硬件下限还差多少，按"差距 × 耗时占比"排序再动手。
做不到时交出：各阶段实测的下限和依据（复杂度、带宽、依赖链），以及要突破下限必须换掉的假设（换算法、换精度、批量化、换硬件）。
```

常见失败：模型悄悄换了口径，或者把"在某个用例上更快"说成"更快"。

实战记录：

### D3 把"做不到"拆成假设
来源：Felix（"它说做不到，就告诉它可以，再试"）｜加入：2026-10-19

用：模型说某件事不可能、太难或者"超出范围"的时候。
别用：它给出的理由是已经证明的数学或物理下限。

```
你说 {X} 做不到，我先不接受这个结论。
把你的推理拆成一张假设清单，每条标注它属于哪一类：数学或物理下限、硬件下限、工程惯性或默认做法。
对每条"惯性"类假设，给出一个绕过方案，并用最小实验验证：给出命令和结果，不要只给论证。
最后告诉我：去掉这些惯性之后，真正的下限在哪里。
```

常见失败：只"再试一次"，但不拆假设，结果第二次撞上同一堵墙。

实战记录：

### D4 从原始数据推翻已有结论
来源：Felix，"挑战你已经认定的结论"；本库补了"等价不等于正确"｜加入：2026-10-19

用：团队里有一个大家默认成立的判断，例如瓶颈在哪、结果为什么对、用户为什么流失。
别用：手里没有原始数据可以复现的时候（先去拿数据）。

```
我们目前认为：{结论}。
请从原始材料（{路径}）出发尝试推翻它，而不是复述它：
- 能不能从原始数据复现这个结论？复现不出来，就说出差在哪里。
- 如果结论是"和参考实现一致所以正确"：两边共有的错误怎么查出来？用不依赖参考实现的东西做对照，例如解析解或人造解、守恒量和恒等式、加密网格后的收敛阶、孪生实验（植入一个已知答案，看能不能恢复）。
- 列出所有没有被检查过的部分，逐个说明为什么可以不查，或者为什么必须查。
输出：推翻或支持这个结论的证据，以及应该新增到验收里的检查。
```

常见失败：模型找到了支持的证据就停了。要明确要求它先找反例。

实战记录：

### D5 找新东西
来源：Felix，"找出新的知识"；Schwartz《Claude-shaped science》（问"什么现在新变得可能"，而不是"什么能更快"）｜加入：2026-10-19

用：一个里程碑刚完成；手里有了新能力，但还没想好怎么用。
别用：主线还没闭环的时候。

```
不要问怎么更快。问：有了 {新能力}，什么事情是现在新变得可能、而一年前做不到或者不划算的？
给出 3 个。每个写清楚：谁会在乎（具体到岗位）、两周内能做出来的最小 demo、用什么外部数据或独立方法证明它成立、如果不成立第几天就能发现。
如果是找规律或找信号：先在 {历史数据} 上重现过去，再找一个我们还不知道的信号，并且在它没见过的数据（{留出集}）上证明它有预测力。
```

常见失败：给出的"新可能"其实是"更快的旧事情"。

实战记录：

### D6 用专家的工具，不用专家的词
来源：Felix，"坚持使用行业顶尖人士所用的工具"｜加入：2026-10-19

用：分析、建模、调研、数据处理。模型习惯用 Markdown 表格和文字推理来代替真正的工具时，尤其要用。
别用：只需要一个快速印象的时候。

```
动手之前，先点名这个领域最强的人做这件事会用的工具和方法，具体到名字（库、求解器、数据库、统计模型、实验设计方法），并说明为什么。
然后真的用它们：装好、跑起来，结果以工具的输出为准。
不要用 Markdown 表格或文字推理代替计算。
```

常见失败：模型点了工具的名字，最后还是用文字推理。要求结果必须带上命令和输出。

## V 验证

### V1 验证器先证明自己会失败
来源：Felix，"引入外部评判"；Schwartz《Claude-shaped science》与 BootLoops 的 planted-truth 协议（每个检查器都要先被看到失败一次，相当于变异测试或正负对照）｜加入：2026-10-19

用：任何要让模型长时间自主跑的任务，在写解法之前用。
别用：已经有一个被验证过的验证器的时候（直接冻结它就行）。

```
写任何解法之前，先为这个任务写验证器。然后证明它有用：
往一个正确的实现里植入 {3} 种不同类型的已知错误（例如数值错、边界条件错、口径错），验证器必须全部抓住。
从来没失败过的检查不算检查。
之后所有"完成了"的说法，都以这个验证器的输出为准，不接受你的自我评价。
```

常见失败：植入的错误太明显，验证器抓住了也说明不了什么。要求至少有一个是"差一点点"的错误。

实战记录：

### V2 独立审查
来源：作者项目里的独立审查做法｜加入：2026-10-19

用：一份报告或一个结论要对外发出、或者要据此做决策之前。
别用：审查者和作者共享同一段上下文的时候，那样就不独立了。

```
你没有参与这项工作。你唯一的目标是找出 {报告或结论} 里不成立的地方。
对每个结论：重新跑它的出处脚本，核对口径（机器、线程数、日期、对照对象、样本范围），找出夸大、缺少限定、换了口径、没有出处的地方。
不要修复，只报告。每一条都要附上你用来复核的命令和输出。
```

常见失败：审查者读的是作者写的摘要，而不是原始记录。要明确给它原始文件。

### V3 证据审计
来源：作者给合作方准备问答时整理的"每次引用数字都要带上的限定"｜加入：2026-10-19

用：对外材料，例如 PPT、报告、邮件、论文。
别用：内部的草稿思考。

```
逐条列出 {材料路径} 里的每一个数字和断言。对每一条：
- 找到原始出处（文件、提交号、脚本），找不到就标"无出处"；
- 对照 {限定清单路径}，检查限定条件带全了没有：验证范围（测试对象还是真实对象）、对比口径（几核对几核、是否同一天测）、对照对象；
- 给出判定：成立 / 缺限定 / 夸大 / 无出处。
不要替我判断"差不多可以"。最后给出改写后的措辞。
```

常见失败：模型把"在阈值以内"自动润色成"完全一致"。

## R 广度

### R1 名词换成动词
来源：Felix，引自 Kelley 与 Littman《The Art of Innovation》｜加入：2026-10-19

用：任务是一个产出物，例如 PPT、报告、文档、demo。
别用：产出物的格式本身就是要求（例如投稿模板）。

```
不要做 "{名词，例如：一份阶段进展 PPT}"。任务是：
在 {时长} 内，让 {谁，具体到角色} 相信 {什么}，同意 {什么决定}，并在结束前定下 {什么下一步}。
先回答：要让他们做到这些，他们必须先相信哪几件事？每件事最有说服力的证据是什么（优先选他们自己能复现的）？
然后再决定产出物的形式和篇幅。越短越好。
```

常见失败：动词化以后，产出还是按老模板填。要求先回答"必须先相信哪几件事"，再谈形式。

### R2 借别的领域的方法
来源：Felix，"组建一支跨领域团队"，加上他对角色扮演的提醒｜加入：2026-10-19

用：卡住了，或者想要一个别人想不到的切入点。
别用：问题在本领域已经有成熟、标准的做法时。

```
把 {任务} 写成一个动词：{动词短语}。
哪些领域长期在解决这个动词？至少列 {4} 个，尽量远离我们自己的领域。
每个领域给出一个他们实际在用的方法或工具（要有名字，能查到），说明怎样在 {两周} 内落到我们的工作里。
不要写成角色对话，直接给方法。
```

例：把一个科学计算程序移植重写成新版本，写成动词是"让一个不认识我们的用户团队，在不读我们代码的前提下，相信并采用一份非原厂实现"。可以借鉴的领域：编译器的翻译验证、航空软件认证、药监的计算机化系统验证、可复现构建、金融模型风险管理。

常见失败：变成角色扮演，对话变得古怪，结果没有变好。

### R3 尽调式审查
来源：Felix，红队和怀疑论者那一段（"按怀疑论者研究投资标的的方法开展调查"）｜加入：2026-10-19

用：对外材料定稿之前。
别用：还在构思阶段的时候（太早审查会把想法扼杀掉）。

```
用技术尽职调查的方法审这份材料，不要写成角色对话：
1. 对方最资深的 {技术岗位} 会先查哪三处？他会在会上提什么问题、做什么 5 分钟内能完成的复现实验？
2. 对方决策人会问哪些和技术无关的问题（许可、交付形式、在哪里运行、谁来维护、出错了谁负责）？哪些我们现在答不上来？
3. 对每个答不上来的问题，写出最诚实的回答，以及会前能补上的最小动作。
```

### R4 多视角并行
来源：Felix，"用子智能体引入其他领域的思路"；调研时搜索配额用光的教训｜加入：2026-10-19

用：大范围调研、多学科选题，或者需要几个独立视角的判断。
别用：问题本身很窄的时候；并行只会多花钱。

```
派 {N} 个子 agent，每个带一个学科或一种方法的视角：{视角列表}。
每个 agent 最多 {20} 次网页搜索；知道 URL 以后，优先直接抓取原始页面（论文、代码仓库、官网）。
每个 agent 交回：结论、证据链接和日期、没核实到的条目（单独列出）。
汇总时只保留有原始出处的内容，并留几次搜索给关键事实做复核（截止日期、许可）。
```

常见失败：多个 agent 共用一份搜索配额，中途同时用光，结论没有核实。

## P 合作方

### P1 还原对方处境
来源：Felix，"高度"一节，用在对方身上｜加入：2026-10-19

用：见合作方、客户或评审之前。
别用：没有任何公开材料可查的对象。

```
从公开的原始材料（对方的论文、设备或产品参数、招聘信息、新闻、项目申报）还原 {合作方} 的处境：
今年要交付什么、卡在哪里、担心什么、内部谁拍板。
然后回答：我们的工作对他们的哪个目标起作用？在什么情况下，"继续合作"对他们来说是最安全的选择，而不是一个风险？
只用有出处的信息，推测单独标出。
```

常见失败：模型凭印象补全了对方的组织结构。要求每一条都带出处。

## S 选题

### S1 选题五问
来源：AI for Science 选题调研中的验证分级筛选（L0–L3，见 contexts.md）；Felix 的"高度"一节｜加入：2026-10-19

用：判断一个方向值不值得投入几个月。
别用：方向已经定了、只差执行的时候。

```
帮我判断 {方向} 值不值得做未来 {6} 个月，按这个顺序：
1. 验证分级：属于 L0（机器即时可验证）到 L3（湿实验、大装置）的哪一级。如果是 L2–L3，能不能先搭一个代理验证器，以及怎么校准它。
2. 前沿：近 6 个月谁在做（论文、代码仓库、榜单）。只列有原始链接和日期的；没核实到的单独列出。
3. 不公平优势：我们的哪项能力在这里起作用（{能力清单，例如：对齐参考实现的软件移植、可审计的计时、可自动评分的证书、独有的数据或算力}）。没有就直说。
4. 止损条件：做到第几周、看到什么结果就停。
5. 极致版本：如果这个方向做到极致，{6} 个月后发出去的是什么？从那里倒推第一周该做什么。
```

常见失败：第 2 条变成一篇综述。要求只列"谁、什么、链接、日期"。

## 反模式

- **角色扮演**。"你现在是 XX 领域专家"只会换一套词汇，方法不变。应该让它说出专家用什么工具，然后真的去用（见 D6）。
- **让模型给自己打分**。每一个"完成"都要对应一个能运行的检查（见 V1、V2）。
- **只给消化过的摘要**。要给原始数据、日志、代码，以及对方的原文。
- **激进目标却不冻结验证器**。得到的会是一次"改了尺子"的达成。
- **把激进目标写进对外材料**。给合作方看的数字，永远用同口径、带限定的那个（见 V3）。
- **所有模式一起叠**。提示词会变得又长又散，关键要求反而被淹没。一次用 2–4 个。
- **小任务写成登月计划**。规模要和任务匹配。
