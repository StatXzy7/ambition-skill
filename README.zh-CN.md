# Ambition

[English](README.md)

一个给 Claude Code 用的提示词改写技能。把你准备发给模型的任务描述交给它，它会往**更高、更深、更广**的方向改写，同时给每个激进目标配上**冻结的外部验证器**。

- **高度**：追问目标背后的目标，而不是停在一个名词（"一份 PPT"）或一个动作（"修这个函数"）上。
- **深度**：给模型原始材料而不是你写的摘要，点名专家真正会用的工具，目标定得激进。
- **广度**：借用长期在解决同一个动词的其他领域的方法。

拉高的同时有一条硬约束。模型被逼紧时，最省事的"达成"方式是悄悄改尺子：放宽阈值、换计时口径、只挑有利的样本。所以改写后的提示词在哪里抬高目标，就在哪里冻结验证器、写明禁止项。另一条原则是做事激进、对外说话保守：给合作方看的数字，一律用同口径、带限定的版本。

技能的说明和模板是中文写的；改写后的提示词使用你提问时用的语言。

## 包含什么

- 改写流程：判断任务类型，诊断最弱的一两个维度，从你的工作目录里取真实的路径和脚本，选 2–4 个模式，交回一份可以直接复制的提示词。
- 一个模式库，共 25 条，分 7 组。每条写明什么时候用、什么时候别用、模板，以及最常见的失败方式。
- 一个任务提示词的通用骨架：用动词写的任务、目标、参照、原始材料、方法、冻结的验证、禁止项、完成的定义、做不到时交出什么。
- 一份 `contexts.md` 模板，用来登记你自己的验证器、原始材料、对外口径和工作区注意事项。登记过的，改写时会直接引用真实文件，而不是留占位符。
- 查看菜单、新增模式、记录模式实战效果的命令。

| 组 | 模式 | 举例 |
| --- | --- | --- |
| H 高度 | H1–H5 | H3：会议以决策收尾，找出最紧迫的三个决策，各附双方的利弊 |
| D 深度 | D1–D6 | D2：定 10 倍目标，同时锁死验证器、阈值和计时脚本 |
| V 验证 | V1–V3 | V1：先植入已知错误，验证器全部抓住才算数 |
| R 广度 | R1–R4 | R1："做 PPT"改成"在 30 分钟内让谁相信什么、决定什么" |
| P 合作方 | P1–P2 | P1：从公开的原始材料还原合作方的处境 |
| S 选题 | S1 | S1：验证分级、前沿、不公平优势、止损条件、极致版本 |
| F 追问 | F1–F4 | F2：检查最近几轮是不是一直停在安全区 |

小任务保持小：改名、修一个已定位的 bug 这类任务，只用一个模式（通常是一条"改动前后行为不变"的检查），控制在 15 行以内。

## 在 Claude Code 里安装

克隆仓库，把技能目录复制到个人技能目录：

```bash
git clone https://github.com/StatXzy7/ambition-skill.git
mkdir -p ~/.claude/skills
cp -r ambition-skill/skills/ambition ~/.claude/skills/
```

如果想只给某个项目用，就复制到那个项目的 `.claude/skills/` 下。如果你已经有一个叫 `ambition` 的技能，先看一下再决定是否覆盖。

然后按自己的项目填写 `~/.claude/skills/ambition/references/contexts.md`。填好的样子见 [examples/contexts.example.md](examples/contexts.example.md)（虚构项目）。不填也能用，只是改写结果里本该是你的真实脚本和路径的地方，会留成 `{需要你填：…}`。

## 用法

```text
/ambition 下周和合作方开会，帮我做一份 PPT 介绍我们项目的进展
/ambition list
/ambition list 验证
/ambition add <一句提示词、一段文章，或者一次好用的经历>
/ambition note D2 <日期｜场景｜好/一般/差｜原因>
```

直接说"帮我改写这个提示词""这个 prompt 怎么写更好""帮我把这个任务想得更高"也会触发。

输出分五部分：两三句诊断、用到的模式和理由、放在一个代码块里的改写后提示词、最多三项只有你能定的事，以及要不要直接执行。

### 示例（节选）

原始提示词：「下周和合作方开会，帮我做一份 PPT 介绍我们项目的进展，希望他们继续合作」

改写后（R1、H3、V3、P1）：

```text
任务：在 {30 分钟} 的会上，让 {合作方的技术负责人} 相信 {我们的实现在他们关心的用例上可用}，
同意 {提供下一批实测数据}，并在结束前定下 {交付日期和验收方式}。
先回答：要让他们做到这些，他们必须先相信哪几件事？每件事最有说服力的证据是什么（优先选他们自己能复现的）？
会议以决策收尾：列出最该推动的三个决策，每个给出可选方案、对双方的利弊、我们希望对方选哪个，以及为什么这个选项对他们也是最优的。
证据审计：材料里的每个数字都要能追到文件、提交号或脚本，带上验证范围和对比口径；找不到出处的标"无出处"。
然后再决定 PPT 的形式和篇幅。越短越好。
{需要你填：合作方是谁、今年要交付什么。}
```

## 来源与局限

模式改写自 Felix Rieseberg 的 [How to be more ambitious: A tutorial for humans with models](https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/)、Matthew D. Schwartz 的 [Claude-shaped science](https://www.anthropic.com/research/claude-shaped-science) 和 [BootLoops 协议](https://github.com/BootLoops-ai/skills)，加上作者在科学软件移植、求解器优化和合作方会议准备中的实践。仓库里不包含原文。见 [NOTICE](NOTICE)。

关于技能有没有用，证据还很少。在作者私有项目的 4 个测试用例上，用技能的回答达成了 28 条期望中的 27 条，不用技能的是 22 条。这只是一次小规模测试，期望也是作者自己写的。本仓库里的测试用例是把那 4 个用例改写成了通用版本，改写后还没有重新跑过。

提示词写得更好，不等于结果就对。让结果可信的是冻结的验证器；技能只能要求你有一个，不能替你造出来或替你检查。

## 参与贡献

欢迎提 issue 和 PR。新增模式时，请附上一个它真正改善过的提示词，以及结果有什么变化；按 `references/patterns.md` 里的"条目格式"写，不要复用已废弃的 ID。请从贡献内容里去掉保密的项目名、路径、合作方信息、未发表的数字和凭据。
